# NailStudio: GitHub and DevOps setup guide

This package adds a starter GitHub Actions CI pipeline. It builds the Android debug APK and runs local JVM unit tests for every push/PR to `main` or `develop`. It uploads the APK as a workflow artifact if both steps succeed.

## 1. Create a GitHub repository
1. Sign in to GitHub and create a new repository named `NailStudio-Android`.
2. Choose **Private** if this is coursework and your lecturer has not asked for a public repository.
3. Do not add a README or .gitignore during creation because these are already in this project.
4. Extract this ZIP. In a terminal, `cd` into the `NailStudioAndroidApp` folder (the one containing `settings.gradle.kts`).
5. Run the commands below, replacing `YOUR-USERNAME` with your GitHub username:

```bash
git init
git add .
git commit -m "Initial NailStudio Android project with CI"
git branch -M main
git remote add origin https://github.com/YOUR-USERNAME/NailStudio-Android.git
git push -u origin main
```

If Git asks you to authenticate, follow GitHub's browser sign-in flow or use GitHub CLI. Do not put access tokens into source files.

## 2. Verify GitHub Actions
1. Open the repository on GitHub.
2. Select **Actions**.
3. Open the `Android CI` workflow.
4. Wait for the run to finish. Green means the configured build and unit tests passed; red means open the failed step and read the first error.
5. For a successful run, open its summary and download the `nailstudio-debug-apk` artifact.

The workflow uses Java 17 and Gradle 8.7. The project does not include a Gradle wrapper, so CI installs Gradle 8.7 directly. For a professional hand-in, consider adding a checked-in Gradle Wrapper generated by Android Studio.

## 3. Use branches and pull requests
- Keep `main` as the stable branch.
- Create a branch per task, e.g. `feature/booking-validation`.
- Commit a small change, push the branch, and open a Pull Request to `main`.
- Wait for the Android CI checks before merging.
- Ask team members to review the PR and record meeting decisions/issues in the repository.

## 4. Suggested DevOps lifecycle evidence
Keep screenshots or notes of each stage for your report:
1. Plan: GitHub Issues and a project board.
2. Code: feature branches and commits.
3. Build: Android Studio build and GitHub Actions build.
4. Test: unit tests, manual device tests, and bug fixes.
5. Release: versioned APK artifact; test on a real Android phone.
6. Operate/monitor: document crash reports, support messages, and a process for handling booking failures.

## 5. Important limits you must complete
- CI is a starter pipeline, not proof the entire app is error-free. Build and run it in Android Studio and test on a physical phone.
- This app's existing authentication and booking storage are local demo functionality. GitHub Actions does not host a backend.
- `database/schema.sql` is a reference PostgreSQL schema and synthetic seed data, not a live database. Provision Azure Database for PostgreSQL (or another approved host), apply the schema, and connect through a secure backend API. Never connect the Android app directly to a database with embedded credentials.
- SSO is not enabled by this ZIP. Choose an identity provider (e.g. Microsoft Entra External ID or Firebase Authentication), register the app, configure redirect URI/client settings, and implement its Android SDK. Do not claim SSO works until sign-in has been tested end-to-end.
- User settings/profile editing still needs to be connected to a persistent profile model and backend if cloud sync is required.
- Put secrets in GitHub Actions **Settings → Secrets and variables → Actions**. Never commit API keys, database passwords, signing keys, tokens, or real customer information.
